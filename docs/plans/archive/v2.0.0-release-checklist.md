## Steps, in order

1. **Bump the version.** In `cmd/lmm/root.go`, change
   `version = "1.30.1"` to `version = "2.0.0"`. Nothing before this checklist
   bumps it (Phase 3's Global Constraints hold `version` at `1.30.1` for the
   whole phase).
2. **Move the CHANGELOG.** In `CHANGELOG.md`, retitle `## [Unreleased]` to
   `## [2.0.0] - <YYYY-MM-DD>` (the actual cut date), leaving a fresh empty
   `## [Unreleased]` heading above it for whatever comes next. Add the
   compare-link footer alongside the existing ones, in the same format every
   prior release uses:

   ```text
   [2.0.0]: https://github.com/DonovanMods/linux-mod-manager/compare/v1.30.1...v2.0.0
   ```

3. **Update the README install line** to match whichever module-path option
   is chosen below (see "OWNER DECISION"). This is the only doc line whose
   wording depends on that choice.
4. **Regenerate man pages.** Run `make man` (`go run ./cmd/lmm gen-man
   docs/man/man1`) and commit the result. `cmd/lmm/genman_test.go` fails the
   build if `docs/man/man1/` drifts from the live command tree, so this step
   isn't optional once the version or any flag/command text has changed.
5. **Commit the prep as one commit** — version bump, CHANGELOG move, README
   line, and regenerated man pages together — mirroring the single
   `release: vX.Y.Z` prep commit the v1.x line uses. PRs are optional on
   `v2` (unlike `develop`/`main`); open one only if an independent review is
   wanted before the tag goes on.
6. **Merge into `v2`.** If the prep happened on a short-lived branch,
   `git merge --no-ff` it into `v2` locally, per the same convention every
   other Phase 3 unit used. If it happened directly on `v2`, there is no
   separate merge commit — the prep commit itself is what gets tagged.
7. **Tag `v2.0.0` on the merge commit** (or the prep commit, if there was no
   separate merge): `git tag v2.0.0 <sha>`.
8. **Push `v2` and the tag** to `nerdwerx` (the remote this project's git
   work goes through).
9. **`develop` and `main` stay untouched.** No fast-forward, no merge of
   `v2` into either branch, no PR targeting `main`. They remain the v1.30.x
   line for existing users; `v2.0.0` lives only on `v2` until a later,
   separate decision promotes it.

## Do not do

- Do not open a PR targeting `main` from this or any `v2` work.
- Do not merge `v2` into `develop`/`main`, or `develop`/`main` into `v2`,
  as part of this cut.
- Do not bump `version` in `cmd/lmm/root.go` before this checklist actually
  runs.

## OWNER DECISION: Go module path (Ruling 14) — Option A chosen

`go.mod`'s module path is currently `github.com/DonovanMods/linux-mod-manager`
(no version suffix). Go's semantic import versioning rule requires a major
version 2 or higher to carry a `/vN` suffix on the module path — and on
every import path that references it — for `go install`/`go get` to resolve
it unambiguously against `@latest`. Whether `v2.0.0` adopts that suffix is
an explicit owner decision; the two options and their consequences follow.

### Option A — adopt `github.com/DonovanMods/linux-mod-manager/v2`

- `go.mod`'s `module` directive changes to add the `/v2` suffix.
- Every internal import in the repo changes to match — currently 290 `.go`
  files import `github.com/DonovanMods/linux-mod-manager/...`, all of which
  need the `/v2` segment inserted. Mechanical (a rewrite, not a redesign)
  but touches nearly every file in one commit.
  README's install command becomes:

  ```bash
  go install github.com/DonovanMods/linux-mod-manager/v2/cmd/lmm@latest
  ```

- `go install .../v2/cmd/lmm@latest` then resolves correctly and
  permanently to the highest `v2.x.y` tag — this is what the Go toolchain
  expects for a major version ≥ 2, so `@latest` behaves the way users
  assume from any other Go tool.
- Cost: the large one-time import rewrite, repeated again if the project
  ever reaches a v3.

### Option B — keep the existing module path

- `go.mod` and every import stay exactly as they are; no rewrite.
- lmm is a single-binary module — `cmd/lmm` is the only consumer, and (per
  the Phase 3 audit) nothing outside this repository imports its internal
  packages as a library — so semantic import versioning's usual purpose
  (letting other modules depend on two major versions of the same package
  at once) doesn't apply here the way it would to a library.
- **The exact risk**: without the `/vN` suffix, Go's module resolution does
  not treat a `v2.0.0+` tag as a valid version for this module path at all.
  `go install github.com/DonovanMods/linux-mod-manager/cmd/lmm@latest`
  would keep resolving to the highest `v1.x` tag (`v1.30.1` today)
  indefinitely — silently never picking up `v2.0.0` or anything after it,
  with no error to warn the installer.
- **Mitigation**: document the install command with an explicit tag instead
  of `@latest`:

  ```bash
  go install github.com/DonovanMods/linux-mod-manager/cmd/lmm@v2.0.0
  ```

  This gets a fresh install onto v2 deliberately. `@latest` remains
  effectively frozen at the last `v1.x` tag until/unless the module path is
  later bumped to add `/v2` (at which point Option A's consequences apply
  retroactively).

**Option A was chosen** (see "Executed" note above). Both options and their
consequences are kept above for the record; Option B's mitigation was not
applied.
